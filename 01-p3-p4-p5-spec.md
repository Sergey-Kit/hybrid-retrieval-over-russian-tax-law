### Запрещённые

**КонсультантПлюс, Гарант** — скрейпинг исключён. См. `00-context-brief.md`, раздел 5.

### Критическое ограничение RusLawOD

В корпус включены **только первые редакции актов**, консолидированных текстов с
поправками нет. Для налоговой нормативки это дисквалифицирующе: НК РФ в редакции
1998 года бесполезен.

**Следствие:** RusLawOD годится как источник подзаконки и как материал для обучения
и оценки, но действующие редакции нужно строить самим. Механика — первая редакция
с pravo.gov.ru плюс последовательное применение ФЗ-поправок как диффов.

Неочевидная ловушка консолидатора: формулировки поправок бывают
структурно-императивными — «дополнить абзацем следующего содержания», «в пункте 3
слова X заменить словами Y», «дополнить статьёй 88.1». Простая замена строк не
работает, нужен парсер инструкций.

## Стек и решения

| Компонент | Решение | Обоснование |
|---|---|---|
| Векторная БД | **Qdrant** или **pgvector** | При объёме до 1–2 млн чанков и потребности в сложных условиях по темпоральности и графу ссылок pgvector проще: фильтр по дате — обычный `WHERE`, обход ссылок — рекурсивный CTE, BM25 через `pg_search`/ParadeDB или `tsvector` в той же СУБД, без синхронизации двух хранилищ. Оценить на этапе проектирования. |
| Эмбеддер | **FRIDA** (SberDevices) или **BGE-M3**. multilingual-e5-large — запасной вариант. | В RusBEIR FRIDA лидирует и соло, и в связке с реранкером; на ruMTEB превысила 70 пунктов. У mE5-large контекст 512 токенов — статья НК не влезает, придётся резать агрессивно. |
| **XLM-R** | **Не использовать как ретривер** | Это энкодер, а не retrieval-модель. Без контрастивного дообучения на парах даст заметно худший результат, чем любой из вариантов выше. Имеет смысл только при наличии датасета пар «требование → релевантная норма», которого пока нет. |
| Лексический поиск | **BM25F по полям** | См. `02-nk-rf-chunking-spec.md`, раздел 3. Критично: префикс в тело для BM25 не добавлять. |
| Лемматизация | **pymorphy3** + пользовательский словарь | Stanza точнее, но на порядок медленнее: для 300k документов это часы против дней. |
| Реранкер | **bge-reranker-v2-m3** | Единственный компонент, видящий запрос и документ совместно. |

## Обязательные требования к ETL

1. **Чанк = пункт статьи**, с исключениями по длине. Схема — в спеке чанкинга, раздел 2.
2. **Иерархический префикс** в dense-поле, отдельные поля для BM25. Раздел 3.
3. **Нормализация ссылок до лемматизации**: `п. 3 ст. 88`, `пункт 3 статьи 88`,
   `п.3 ст.88` → единая форма. Иначе BM25 не найдёт совпадение по самому
   информативному токену запроса.
4. **Стоп-слова отключить.** Стандартный русский стоп-лист выкидывает «не», «либо»,
   «иной» — в праве это несущие слова. IDF справится сам.
5. **Извлечение графа внутренних ссылок** с типизацией (`procedure`, `exception`,
   `definition`, `sanction`). Раздел 4. Ссылки типа `exception` — самые ценные для
   задачи «обязан ли представлять».
6. **Четыре даты** на версию нормы: `published_at`, `valid_from`, `valid_to`,
   `applies_from`. Основной фильтр для налоговой задачи — `applies_from`. Раздел 5.
7. **Даты как int в формате YYYYMMDD**, `valid_to = 99991231` вместо `null`.

## Что измерить и показать

- Recall@k и nDCG@10: чистый dense vs BM25 vs гибрид vs гибрид + реранкер.
- Отдельно на коротких запросах («срок ответа на требование») и на запросах с
  точными лексическими якорями («п. 3 ст. 88»).

**Ожидаемый результат:** гибрид выиграет у чистого dense с бо́льшим отрывом, чем в
типовых бенчмарках. В RusBEIR BM25 подтверждён как сильный baseline на
full-document retrieval и лучше нейронных моделей на длинных текстах. Статьи НК
длинные, запросы содержат точные ссылки. Готовиться к тому, что BM25-ветка окажется
не подпоркой, а основным каналом.

## Критерии приёмки P3

- [ ] Индекс содержит НК РФ ч. 1 и 2 в консолидированных редакциях минимум за
      последние 5 лет, с корректными датами действия.
- [ ] Recall@20 гибрида ≥ 0.9 на golden set из P4.
- [ ] Фильтр по `applies_from` не роняет recall более чем на 5 п.п.
- [ ] Замерен recall против brute force — числа `ef`/`M` из туториалов не брать,
      они для нефильтрованных коллекций.

# P4. Харнесс оценки

## Golden set

**Не существует** размеченного набора «требование ФНС → правильный ответ» ни в
открытом доступе, ни в закрытом. Это одновременно наш моат и наше узкое место.

### Состав

Минимум 150–300 пар, собранных **с практикующим налоговым юристом**. Разбивка:

| Категория | Доля | Комментарий |
|---|---|---|
| Требования в рамках камеральной проверки (ст. 88) | ~30% | Самый частый тип |
| Истребование документов у проверяемого (ст. 93) | ~20% | |
| Встречные требования (ст. 93.1) | ~20% | Здесь больше всего злоупотреблений |
| Вызов на комиссию, пояснения вне проверки | ~10% | |
| **Негативы** | **≥20%** | См. ниже |

### Негативы обязательны

Три типа:

1. Требование, на которое отвечать не нужно или нужно частично.
2. Вопрос, на который в открытых источниках нет основания для ответа — правильный
   ответ системы «не знаю».
3. Вопрос с датой, для которой применимая редакция отличается от текущей.

**Без негативов метрики измеряют красноречие, а не правильность.**

### Обязательное поле

У каждого вопроса — **`as_of`**, дата, на которую проверяется применимая редакция.
Без неё темпоральную корректность измерить невозможно.

## Метрики

| Метрика | Что ловит |
|---|---|
| Recall@k, MRR, nDCG — без темпорального фильтра | Качество ретривера как такового |
| Recall@k — с фильтром | Не режет ли фильтр правильные ответы |
| **Temporal accuracy** | Доля ответов, процитировавших редакцию, действовавшую на `as_of` |
| Reference completeness | Доля случаев, где найдены все нормы из ссылок эталона |
| Claim-level faithfulness (claim extraction + NLI-судья) | Не выдумана ли норма |
| Answer relevance, context relevance (RAGAS) | Стандартные |
| **Abstention accuracy** | Доля корректных отказов на негативах типа 2 |

### Главная метрика продукта — temporal accuracy

Faithfulness может показывать 0.95 при temporal accuracy 0.6: модель честно цитирует
найденный чанк, просто чанк из редакции 2022 года. Мерить отдельно, выносить на
дашборд первой строкой.

## Критерии приёмки P4

- [ ] Golden set ≥150 пар, ≥20% негативов, у каждого вопроса есть `as_of`.
- [ ] Разметка выполнена или верифицирована доменным экспертом, а не только инженером.
- [ ] Дашборд показывает все метрики выше с разбивкой по типам требований.
- [ ] Прогон воспроизводим одной командой, результаты версионируются.

# P5. Флагман: on-prem ассистент

## Функциональные требования

### Слой 1 (первая версия) — справочно-фактический

На входе файл требования (PDF, скан, DOCX). На выходе:

1. **Тип требования** и правовое основание (статья НК).
2. **Сроки**: дата получения, срок направления квитанции, срок ответа, крайняя дата.
   С учётом рабочих/календарных дней и переносов.
3. **Перечень истребуемого** — структурированный список того, что запрошено.
4. **Объём обязанности**: что относится к предмету запроса, а что выходит за его
   рамки. Со ссылками на нормы.
5. **Последствия неответа**: применимые санкции со ссылками.
6. **Черновик ответа** с обязательными ссылками на источники.

### Слой 2 (после накопления данных) — не проектировать сейчас

Правомерность требования, основания мотивированного отказа, стратегия ответа,
прогноз риска. Требует юриста в контуре и накопленной статистики.

## Нефункциональные требования

| Требование | Уточнение |
|---|---|
| **Отсутствие сетевых вызовов в рантайме** | Ни эмбеддера, ни LLM, ни поиска, ни телеметрии. Проверяется тестом: работа при полностью отключённой сети. Это демонстрируемое свойство и главный продающий аргумент. |
| **Целевое железо** | Одна потребительская GPU 24 ГБ либо CPU-сервер. Конкретная модель и вариант квантизации — из результатов P2. |
| **Обновление корпуса** | Офлайн-пакетами: подписанный архив, импорт из файла. Никакой онлайн-синхронизации. |
| **Разграничение доступа** | По клиентам внутри инсталляции (заменяет «гриф доступа» из роадмапа). |
| **Логирование** | Каждый запрос, показанные чанки, выбранный ответ, пометки «неверно». Внутри инсталляции. Экспорт обезличенной статистики — только по явному согласию клиента. |

## Архитектурные требования против галлюцинаций

Это не настройки промпта, а свойства системы.

1. **Утверждение без цитаты не показывается.** Постпроцессор проверяет наличие
   привязки к `chunk_id` для каждого фактического утверждения. Не прошедшее —
   вырезается, а не помечается.
2. **Явный отказ.** Если после ретрива и реранка confidence ниже порога либо
   релевантных чанков нет — ответ «в базе нет основания». Отказ предпочтительнее
   правдоподобного вымысла.
3. **Цитата ведёт к точному месту.** `chunk_id` резолвится до статьи, пункта и
   абзаца — метаданные это позволяют (`para_offsets`).
4. **Показ редакции.** В интерфейсе рядом с каждой нормой видна дата редакции, по
   которой дан ответ. Пользователь должен видеть, что система знает про даты.
5. **Формулировки без вердиктов.** «Найдены следующие нормы» — да. «Требование
   незаконно» — нет. Единообразно в UI, в выводе модели и в договоре.

## Пайплайн запроса

```
1. Парсинг файла требования (OCR при необходимости)
2. Классификация: тип требования, as_of, налог, реквизиты
3. Фильтр по метаданным  ← ДО ANN-поиска, не после
4. Dense top-50 ∥ BM25 top-50
5. RRF-слияние: score = RRF(k=60) * authority * recency_boost
6. One-hop expansion по refs_out (procedure, exception, definition)
7. Реранкер на top-30 → top-8
8. Генерация локальной LLM с обязательными цитатами
9. Постпроцессор: проверка цитат, вырезание непривязанного
10. Логирование
```

Порядок шага 3 принципиален: фильтрация после ANN-поиска теряет кандидатов.

## Критерии приёмки P5

- [ ] Работает при физически отключённой сети — записать демо.
- [ ] Temporal accuracy ≥0.85 на golden set из P4.
- [ ] Claim-level faithfulness ≥0.9.
- [ ] Abstention accuracy ≥0.8 на негативах.
- [ ] Каждое фактическое утверждение в выводе имеет резолвящуюся ссылку.
- [ ] Развёртывание на целевом железе одной командой, инструкция проверена
      посторонним человеком.
- [ ] Проведён живой прогон минимум с одним реальным бухгалтером на его требованиях.

# Сквозные соглашения

## Схема идентификаторов

```
norm_unit    nk1/st88/p3           стабильная норма, живёт вечно
norm_version nk1/st88/p3@r7        текст в интервале действия
chunk        nk1/st88/p3@r7#0      то, что лежит в векторной БД
```

Разделитель — `/`, **не точка**: статьи и пункты содержат точки в номерах
(ст. 93.1, п. 8.1).

## Порядок работ

```
P3 ──┬──► P4 ──► P5
     │
     └─► корпус и ETL переиспользуются полностью
```

P3 и P4 строить **сразу на реальном корпусе НК РФ и реальных требованиях**, не на
учебном датасете. Тогда это один и тот же код, а не «сначала практика, потом продукт».

## Что взять из уже сделанного

- **Из P1:** выбор рантайма под целевую нагрузку on-prem-инсталляции.
- **Из P2:** конкретный вариант квантизации под 24 ГБ VRAM, точка на кривой Парето.
  Калибровка AWQ на доменных данных — если делалась, использовать налоговый корпус.

## Открытый вопрос, влияющий на объём

Участие доменного эксперта. См. `00-context-brief.md`, раздел 6. Если эксперта нет —
слой 1 строится строго справочным, без единой правовой оценки, а пункт 4
функциональных требований («объём обязанности») сокращается до перечисления
запрошенного без суждения о его правомерности.
