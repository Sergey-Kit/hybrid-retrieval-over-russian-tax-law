# Чанкинг и темпоральная модель для RAG по НК РФ

Спецификация под стек: Qdrant (или pgvector) + dense-эмбеддер + BM25 с лемматизацией.

---

## 0. Три вещи, которые ломают юридические RAG'и

Прежде чем схема — три ошибки, из-за которых такие системы отвечают уверенно и неверно.

1. **Чанк без иерархического контекста.** Текст «3. При выявлении ошибок в налоговой декларации... налоговый орган сообщает об этом налогоплательщику с требованием представить пояснения» — сам по себе не содержит слов «камеральная проверка», «пять дней», «статья 88». Dense-ретривер его не найдёт, а LLM не поймёт, откуда он.

2. **Отсутствие среза на дату.** Требование от 2024 года проверяется по редакции, действовавшей в 2024 году. Индекс, где лежит только «сейчас», даёт правдоподобно-неверный ответ на любой ретроспективный вопрос — а их в налоговой практике большинство.

3. **Неразрешённые внутренние ссылки.** НК устроен как граф: «в порядке, предусмотренном статьёй 93.1 настоящего Кодекса», «в случаях, указанных в пункте 8.1 настоящей статьи». Без обхода ссылок ответ будет формально верным и практически бесполезным.

## 1. Иерархия НК РФ

```
Часть (первая / вторая)
└── Раздел (римская нумерация)
    └── Глава (арабская)
        └── Статья           ← 88, 93, 93.1, 129.1
            └── Пункт        ← 1, 2, 3, 8.1
                └── Подпункт ← 1), 2), 3)
                    └── Абзац ← без номера, но цитируется как «абзац второй»
```

Особенности, которые обязательно надо заложить в парсер:

- **Статьи с точкой** (93.1, 88.1, 105.14) — это не «пункт 1 статьи 93», а самостоятельные статьи, вставленные поправками. Разделитель ID не может быть точкой.
- **Пункты с точкой** (п. 8.1 ст. 88) — по той же причине.
- **Утратившие силу пункты** остаются в тексте как «Пункт 4. — Утратил силу». Их надо парсить и хранить: на них ссылаются старые требования.
- **Абзацы не нумеруются в тексте**, но нумеруются в ссылках и в требованиях ИФНС. Нумерация — сквозная внутри пункта, считая с первого абзаца самого пункта.
- **Примечания и сноски** к статье относятся ко всей статье, не к пункту.

## 2. Единица чанка: пункт

**Правило по умолчанию: один пункт статьи = один чанк.**

Обоснование:

| Вариант | Проблема |
|---|---|
| Статья целиком | ст. 88 — несколько тысяч токенов. Не влезает в контекст mE5 (512). Ретривер находит статью, но LLM тонет в нерелевантных пунктах. |
| Подпункт | Теряется смысл: подпункт 1) п. 1 ст. 31 без вводной фразы пункта — обрывок предложения. |
| Фиксированное окно (512/1024 с overlap) | Рвёт нормы посередине. Категорически не подходит для права. |
| **Пункт** | Совпадает с единицей цитирования в требованиях ИФНС («в порядке п. 3 ст. 88 НК РФ»). Самодостаточен по смыслу. Обычно 80–600 токенов. |

**Два исключения:**

- **Пункт длиннее `MAX_TOKENS` (рекомендую 700).** Дробим по подпунктам. Каждый подпункт-чанк наследует полный префикс + вводную фразу пункта. Пример: п. 1 ст. 31 НК (права налоговых органов) — 15 подпунктов, обязательно дробить.
- **Статья короче `MIN_TOKENS` (рекомендую 120) или не имеет пунктов.** Чанк = статья целиком.

**Никогда не режем:** одно предложение между чанками, перечисление от его вводной фразы, условие от его последствия.

## 3. Наследование контекста

Каждый чанк получает синтетический иерархический префикс:

```
Налоговый кодекс Российской Федерации, часть первая
Раздел V. Налоговый контроль
Глава 14. Налоговый контроль
Статья 88. Камеральная налоговая проверка
Пункт 3
Редакция действует с 01.01.2026
———
[текст пункта]
```

### Критично: префикс по-разному ведёт себя в dense и в BM25

Это место, где чаще всего теряется качество гибрида.

- **Dense:** префикс нужен целиком. Он даёт эмбеддингу тему («камеральная проверка», «налоговый контроль»), которой в теле пункта может не быть ни разу.
- **BM25:** префикс, добавленный в тело, **уничтожает различимость**. Все 15 чанков статьи 88 получают одинаковые высокочастотные токены «камеральный», «проверка», «статья», «88». IDF по ним падает, ранжирование внутри статьи становится случайным.

**Решение — раздельные поля в индексе:**

```python
{
  "text_dense":  full_prefix + "\n———\n" + body,   # идёт в эмбеддер
  "text_bm25":   body,                              # только тело
  "title_bm25":  article_title + " " + clause_ref,  # отдельное поле, вес ~0.3
}
```

BM25 считаем как взвешенную сумму по полям (BM25F) либо два отдельных индекса со слиянием. Веса подбирайте на своём golden set; стартовая точка — `body: 1.0, title: 0.3`.

### Лемматизация для BM25

- pymorphy3 — быстрее, достаточно для юридической лексики, но не снимает омонимию по контексту.
- Stanza — точнее, на порядок медленнее. Для 300k документов ETL это часы против дней.

**Рекомендация:** pymorphy3 + пользовательский словарь юридических аббревиатур и исключений. Обязательно добавьте:

- Нормализация ссылок в единую форму **до** лемматизации: `п. 3 ст. 88`, `пункт 3 статьи 88`, `п.3 ст.88`, `ч. 3 ст. 88` → `пункт_3_статья_88`. Иначе BM25 не найдёт точное совпадение по самому информативному токену запроса.
- Не лемматизировать номера, даты, коды КБК/ОКВЭД.
- Стоп-слова: собственный список. Стандартный русский стоп-лист выкидывает «не», «либо», «иной» — в праве это несущие слова. **Стоп-слова для юридического BM25 лучше отключить полностью**, IDF справится сам.

## 4. Внутренние ссылки как граф

На этапе парсинга извлекаем все ссылки регулярками + постобработкой:

```python
refs_out = [
  {"target": "nk1/st93.1",        "type": "procedure", "raw": "статьёй 93.1 настоящего Кодекса"},
  {"target": "nk1/st88/p8.1",     "type": "exception", "raw": "пунктом 8.1 настоящей статьи"},
  {"target": "nk1/st129.1",       "type": "sanction",  "raw": "статьёй 129.1"},
]
```

Типы ссылок (размечаются эвристиками по глаголу-связке):

- `procedure` — «в порядке, установленном…»
- `exception` — «за исключением случаев…», «если иное не предусмотрено…»
- `sanction` — «влечёт ответственность, предусмотренную…»
- `definition` — «в значении, определённом…»
- `amendment` — служебная, для истории редакций

**One-hop expansion на retrieval:** после гибридного поиска берём top-k, дотягиваем чанки по `refs_out` с типами `procedure`, `exception`, `definition`, помечаем их как `expanded: true` и ставим в конец контекста. Дёшево, детерминированно и закрывает класс ошибок, который dense-ретривер не закроет никогда.

Ссылки типа `exception` — самые важные для вашей задачи «отвечать или не отвечать». Именно там живут основания не исполнять требование.

## 5. Темпоральная модель

### Три уровня сущностей

```
norm_unit    — стабильная норма, живёт вечно.     nk1/st88/p3
   └── norm_version — текст в интервале действия.  nk1/st88/p3@r7
          └── chunk — то, что лежит в Qdrant.      nk1/st88/p3@r7#0
```

Один `norm_unit` порождает N версий за свою жизнь. Один `norm_version` порождает 1..M чанков (M>1 только при дроблении длинного пункта).

### Четыре разные даты — не путать

Это главная ловушка. У одной поправки их четыре, и они не совпадают:

| Поле | Что означает | Пример |
|---|---|---|
| `published_at` | Дата официального опубликования | 28.11.2025 |
| `valid_from` | Дата вступления редакции в силу | 01.01.2026 |
| `valid_to` | Дата утраты силы (exclusive) | `99991231` для действующих |
| `applies_from` | Дата, с которой норма применяется к правоотношениям | 01.01.2025 (ретроспективно!) |

Реальный кейс: ФЗ от 28.11.2025 № 425-ФЗ скорректировал порядок камеральных проверок и истребования пояснений по НДС — опубликован в ноябре 2025, вступил в силу с 01.01.2026. Если в системе только одна дата, ответы на требования за IV квартал 2025 будут неверными.

**Для налогового RAG основной фильтр — `applies_from`, а не `valid_from`.** Вопрос пользователя «требование по декларации за 2025 год» означает «какая норма применялась к правоотношениям 2025 года», а не «какая норма действовала на дату требования.

### Схема payload

```json
{
  "chunk_id":      "nk1/st88/p3@r7#0",
  "norm_unit_id":  "nk1/st88/p3",
  "version_id":    "nk1/st88/p3@r7",

  "code":          "НК РФ",
  "part":          1,
  "section":       "V",
  "chapter":       14,
  "article":       "88",
  "article_title": "Камеральная налоговая проверка",
  "clause":        "3",
  "subclause":     null,
  "para_offsets":  [[0, 210], [211, 480]],

  "valid_from":    20260101,
  "valid_to":      99991231,
  "applies_from":  20260101,
  "published_at":  20251128,
  "status":        "active",

  "enacted_by":    "ФЗ от 31.07.1998 № 146-ФЗ",
  "amended_by":    "ФЗ от 28.11.2025 № 425-ФЗ",
  "version_no":    7,

  "source_type":   "norm",
  "tax":           ["НДС", "прибыль", "НДФЛ", "УСН"],
  "req_type":      ["88", "93", "93.1"],
  "topic":         ["камеральная_проверка", "пояснения"],

  "refs_out":      ["nk1/st93.1", "nk1/st88/p8.1"],
  "refs_in":       ["nk1/st129.1", "nk1/st100/p5"],

  "text_dense":    "...",
  "text_bm25":     "...",
  "title_bm25":    "...",
  "authority":     1.0
}
```

### Практические решения по полям

**Даты как `int` в формате `YYYYMMDD`, не как timestamp и не как строка.** Range-фильтры в Qdrant по integer работают быстрее, сравнение читаемо в логах, нет часовых поясов.

**`valid_to = 99991231` вместо `null`.** Фильтрация по `is_null` в Qdrant дороже range-условия и хуже комбинируется с payload-индексом. Sentinel-значение делает фильтр однородным:

```python
Filter(must=[
    FieldCondition(key="applies_from", range=Range(lte=as_of)),
    FieldCondition(key="valid_to",     range=Range(gt=as_of)),
])
```

**`authority`** — вес источника при слиянии. Норма 1.0, письмо ФНС 0.7, решение по жалобе 0.6, судебный акт ВС 0.8, суд первой инстанции 0.3. Умножается на итоговый score после RRF.

**`req_type`** — под вашу целевую задачу. Позволяет на входе классифицировать требование и сразу сузить поиск до релевантного среза.

## 6. Конфигурация Qdrant

### Payload-индексы (обязательно)

```python
for field in ["applies_from", "valid_to", "valid_from"]:
    client.create_payload_index(collection, field,
                                field_schema=PayloadSchemaType.INTEGER)

for field in ["article", "status", "source_type", "tax", "req_type"]:
    client.create_payload_index(collection, field,
                                field_schema=PayloadSchemaType.KEYWORD)
```

### Проблема фильтрованного HNSW

При сильной фильтрации (а темпоральный фильтр отсекает большинство точек) HNSW теряет recall: обход графа уходит в отфильтрованные регионы и упирается в `ef` до того, как наберёт кандидатов. Qdrant умеет переключаться на brute force, если после фильтра осталось мало точек — но порог надо задать явно.

**Вариант A (проще и быстрее):** разделить на две коллекции.

- `nk_current` — только действующие редакции (`valid_to = 99991231`). Покрывает ~90% запросов, фильтр по дате не нужен вообще, HNSW работает в полную силу.
- `nk_historical` — все версии, включая утратившие силу. Запрашивается только когда в вопросе есть явный ретроспективный период.

Роутинг делает классификатор запроса на входе: извлёк период → идёт в historical, не извлёк → current.

**Вариант B:** одна коллекция + тюнинг.

```python
hnsw_config=HnswConfigDiff(
    m=32,                      # для ~500k чанков; 16 маловато при фильтрах
    ef_construct=256,
    full_scan_threshold=20000, # ниже этого — brute force, точный результат
    payload_m=16,              # доп. рёбра внутри payload-групп
)
```

`payload_m` строит дополнительные связи внутри групп по индексированному payload-полю — именно то, что нужно при постоянной фильтрации по одному полю. Задаётся вместе с `on_disk_payload=False`.

Поиск: `ef` в диапазоне 128–256. Замеряйте recall@50 против brute force на своём golden set — не берите числа из туториалов, они для нефильтрованных коллекций.

### pgvector — когда он лучше

Если объём до ~1–2 млн чанков и вам нужны сложные SQL-условия по темпоральности и графу ссылок — pgvector с HNSW проще в эксплуатации. Темпоральный фильтр становится обычным `WHERE`, планировщик сам выберет стратегию, а рекурсивный обход `refs_out` пишется одним CTE. Плюс BM25 через `pg_search`/ParadeDB или `tsvector` — всё в одной СУБД, без синхронизации двух хранилищ. Для вашего объёма это, возможно, правильный выбор.

## 7. Гибридное слияние

```
score = RRF(dense_rank, bm25_rank, k=60) * authority * recency_boost
```

`recency_boost` = 1.0 для действующей редакции, 0.85 для предыдущей, если запрос не содержит явного периода. Не отсекайте старые редакции жёстко — иногда именно они и нужны.

Порядок операций строго такой:

1. Классификация запроса → извлечение `as_of`, `req_type`, `tax`
2. Фильтр по метаданным (**до** ANN-поиска, не после — иначе теряете кандидатов)
3. Dense top-50 + BM25 top-50 параллельно
4. RRF-слияние
5. One-hop expansion по `refs_out`
6. Реранкер (bge-reranker-v2-m3) на top-30 → top-8
7. Сборка контекста

Реранкер здесь не роскошь: он единственный компонент, который видит запрос и документ совместно и способен отличить «норма про этот случай» от «норма про похожий случай».

## 8. Другие типы источников

Одна схема на всё не натягивается. Кратко:

**Письма Минфина/ФНС** — атомарны. Весь документ = 1 чанк, если < 700 токенов, иначе разбить на «вопрос» / «позиция» / «обоснование». Метаданные: `source_type: "letter"`, `refs_out` на нормы (обязательно извлекать), `authority: 0.7`, `is_binding` (обязательно ли для применения налоговыми органами).

**Решения по жалобам ФНС** — извлекать три блока: «доводы налогоплательщика», «позиция налогового органа», «вывод». В индекс идут вывод и позиция; доводы — в payload для показа пользователю. `authority: 0.6`, метаданные `outcome: удовлетворена | частично | отказано`.

**Судебные акты** — чанк = абзац мотивировочной части. Метаданные: `instance`, `court`, `date`, `outcome`, `refs_out` на нормы. Обязательно `is_current_practice` — позиция может быть пересмотрена, и устаревшая практика опаснее её отсутствия.

## 9. Что мерить

Golden set обязан содержать `as_of` в каждом вопросе. Метрики раздельно:

| Метрика | Что ловит |
|---|---|
| Recall@k без темпорального фильтра | качество ретривера как такового |
| Recall@k с фильтром | не режет ли фильтр правильные ответы |
| **Temporal accuracy** | доля ответов, процитировавших редакцию, действовавшую на `as_of` |
| Reference completeness | доля случаев, где найдены все нормы из ссылок эталона |
| Claim-level faithfulness (ваш NLI-судья) | не выдумал ли LLM норму |

**Temporal accuracy — главная метрика вашего продукта.** Faithfulness может быть 0.95 при temporal accuracy 0.6: модель честно цитирует найденный чанк, а чанк — из редакции 2022 года.

Обязательная доля негативов в golden set: вопросы, где правильный ответ — «в открытых источниках нет основания», и требования, на которые отвечать не нужно. Без них метрики измеряют красноречие, а не правильность.
