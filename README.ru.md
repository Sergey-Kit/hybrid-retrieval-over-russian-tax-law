# P3 — гибридный retrieval по налоговой нормативке РФ

Поиск по Налоговому кодексу с темпоральной корректностью: не «что написано в НК», а
**«что было написано в НК на такую-то дату»**. Генерации здесь нет и не будет — граница
проекта проходит по возврату правильных фрагментов нормы.

Техническое задание — [`P3_retrieval_SPEC.md`](P3_retrieval_SPEC.md). Этот файл описывает
**фактическое состояние**, включая места, где реальность разошлась с ТЗ, и места, где я
ошибался и это обнаружилось замером.

```bash
pip install -r requirements.txt && python -m pytest -q     # 287 тестов
```

## Результаты

Цифры посчитаны **один раз на held-out test**; тюнинг весов шёл только на train.
Таблицы собираются из файлов замеров командой `p3 render-results`, а не переписываются
руками — иначе они молча расходятся с данными при следующем прогоне.

### Silver set, test

Достижимо **331 запросов из 337** (98%). Метрики считаются на достижимом
подмножестве — запросах, чей эталон присутствует в индексе, — и доля печатается
рядом с цифрами: молча отфильтровать было бы приукрашиванием, только незаметным.

| Конфигурация | recall@20 | hit@20 | recall@8 | nDCG@10 | MRR | мс |
|---|---|---|---|---|---|---|
| Чистый dense | 0.665 | 0.737 | 0.589 | 0.490 | 0.503 | 96 |
| Чистый BM25 | 0.682 | 0.764 | 0.556 | 0.451 | 0.458 | 16 |
| **Гибрид (RRF)** | 0.689 | 0.767 | 0.627 | 0.527 | 0.533 | 24 |
| Гибрид + реранкер | 0.596 | 0.680 | 0.596 | 0.536 | 0.563 | 17591 |

Потолок recall@20 на этом корпусе — 0.997: эталон почти полностью
присутствует в индексе, и метрика не ограничена его неполнотой.

### Синтетический набор слоя 1 (эталон на уровне пункта)

| Конфигурация | recall@20 | hit@20 | recall@8 | nDCG@10 | MRR | мс |
|---|---|---|---|---|---|---|
| Чистый dense | 0.819 | 0.889 | 0.736 | 0.555 | 0.527 | 64 |
| Чистый BM25 | 0.639 | 0.694 | 0.611 | 0.560 | 0.586 | 10 |
| **Гибрид (RRF)** | 0.819 | 0.889 | 0.778 | 0.666 | 0.666 | 16 |
| Гибрид + реранкер | 0.847 | 0.917 | 0.847 | 0.804 | 0.838 | 15304 |

Потолок recall@20 на этом корпусе — 1.000: эталон почти полностью
присутствует в индексе, и метрика не ограничена его неполнотой.

Реранкер отдаёт top-8, поэтому его `recall@20` ограничен восемью позициями и по этой
колонке несопоставим с конфигурациями, возвращающими 50. Его следует сравнивать по
`recall@8`, `nDCG@10` и `MRR`.

### Главный замер: цена живого языка

Одна норма, один эталон, две формулировки:

| Формулировка | recall@20 | nDCG@10 |
|---|---|---|
| Выдержка из требования (якорь есть) | 0.861 | 0.860 |
| Живой вопрос (якоря нет) | 0.778 | 0.472 |

### Темпоральный тест (`hybrid`)

70 синтетических запросов «редакция на дату», эталон — конкретная версия нормы.

| | |
|---|---|
| Возвращена верная редакция | **64%** |
| Возвращена чужая редакция нужной нормы | **0** |
| Норма не найдена вовсе | 25 |
| Цена фильтра относительно индекса одной редакции | **0.0 п.п.** (порог ТЗ: 5.0) |

Ноль во второй строке — главная цифра: когда норма найдена, редакция всегда верная,
значит промахи это отказы поиска, а не темпоральной модели. Чужая редакция опаснее
ненайденной нормы, потому что выглядит правильным ответом.

Цена фильтра меряется относительно индекса **одной редакции**: recall@20 равен
0.7639 и там, и в темпоральном индексе с фильтром. Фильтр возвращает систему ровно
к базовой линии, добавляя при этом возможность отвечать на любую дату.

Сравнивать с нефильтрованным индексом всех версий нельзя: там одна норма
представлена несколькими версиями, любая засчитывается как попадание, и recall@20
выходит 0.8194 — на 5.55 п.п. выше исключительно за счёт дублей. Такой индекс вдобавок
выдаёт устаревшие редакции, то есть не является системой, которую можно поставить.


---

## Headline

**Темпоральный фильтр стоит 0.00 п.п. recall.** Индекс одной редакции и темпоральный индекс
с фильтром дают одинаковый recall@20 = 0.7639. Система получает способность отвечать на
любую дату, не теряя качества. При этом когда норма найдена, **редакция всегда правильная** —
ноль случаев чужой редакции на 70 запросах.

**Живой язык стоит 45% качества ранжирования.** Одна норма, один эталон, две формулировки:
выдержка из требования даёт nDCG@10 = 0.860, вопрос бухгалтера — 0.472. Норма находится
почти так же часто (recall 0.861 против 0.778), но перестаёт быть наверху.

**Гибрид бьёт оба канала** на 331 запросе: recall@20 0.689 против 0.665 у dense и 0.682 у
BM25. Реранкер меняет полноту на порядок — на слое 1 он выигрывает всё сразу
(recall@8 0.847, MRR 0.838), на silver теряет 3.2 п.п. полноты, выигрывая MRR.

## Три вещи, которых обычно нет

**Темпоральная корректность.** 5 редакций части первой за 2019–2026 сведены в 1692 нормы и
2894 версии; 821 норма менялась. Фильтр `valid_from <= as_of < valid_to` применяется **до**
поиска в обоих каналах. Подробности и границы применимости: [`docs/temporal.md`](docs/temporal.md).

**Оценка без ручной разметки.** 1678 пар «запрос → нормы», собранных автоматически из
решений по жалобам и писем ФНС, где разметку статьями делает само ведомство. Плюс
синтетический набор слоя 1, где эталон известен по построению и проверяется против корпуса.
[`docs/silver-set.md`](docs/silver-set.md), [`docs/data-sources.md`](docs/data-sources.md).

**Отрицательные результаты записаны.** Проверенные и отвергнутые источники, включая причины
отказа, лежат в [`docs/data-sources.md`](docs/data-sources.md) — чтобы никто не проверял их заново.

## Тихие дефекты, найденные на реальных данных

Все они не падают, не логируются и дают правдоподобные цифры. Каждый закрыт тестом.

| Дефект | Что было бы |
|---|---|
| Надстрочные индексы: «Статья 6¹» → «Статья 61» | теряется **половина статей**, включая 6.1, 93.1, 101.4, 129.1 — ядро процедурных норм |
| `rdk` не хронологичен (212 от 2020, 197 от 2022) | интервалы действия строятся задом наперёд; фильтр работает, но выбирает не те версии |
| Смена вёрстки ИПС около 2019 | парсер вернул 0 статей на документе в 1.5 МБ и промолчал |
| Без `print=1` ИПС отдаёт начало документа | 25 статей вместо 142, обрыв на середине предложения, `page` принимается и игнорируется |
| Точка в токене ссылки | `nk1_st93.1` рвётся на `nk1_st93` и `1` |
| Нормировка длины по документу, а не по полю | точная ссылка с IDF 6.6 проигрывает частотным словам в коротком документе |
| «НК РФ» как отдельные слова | «рф» встречается в 2 документах из 1906, получает IDF 6.64 и перебивает саму цитату |
| Префикс в поле BM25 | все 27 чанков статьи 88 получают одинаковые токены, ранжирование внутри статьи становится случайным |
| Ссылка без названия кодекса | «статьей 5 Федерального закона» становится нормой НК |
| `norm_unit_id` в своём формате | пересечения с эталоном пусты, recall тихо занижен |

Отдельно — **две ошибки в самих измерениях**, найденные после получения чисел:

**Вклад one-hop показывал 0.0%**, потому что раскрытые ссылки дописывались в конец списка из
сотни результатов, а мерилось top-20. Ноль был свойством измерения, а не графа.

**Цена темпорального фильтра показывала 5.55 п.п.** и проваливала критерий ТЗ, потому что
сравнивалась с нефильтрованным индексом всех версий. Там одна норма представлена несколькими
версиями, любая засчитывается как попадание — у поиска просто больше попыток. Относительно
правильной базы цена равна нулю.

## Устройство

```
src/p3/
  config.py netcheck.py raw_store.py fetch.py   сбор: троттлинг, кэш, происхождение
  refs/normalize.py      «подпунктом 2 пункта 1 статьи 31» -> nk1/st31/p1/sp2
  sources/ips.py         ИПС: поиск, редакции, полные тексты
  sources/nalog_ru.py    решения по жалобам ФНС
  sources/fns_letters.py письма, обязательные для применения
  nk/parse.py            раздел -> глава -> статья -> пункт
  nk/refs.py             граф ссылок с типами
  nk/chunk.py            чанкинг, text_dense / text_bm25 / title_bm25
  nk/temporal.py         версии норм и интервалы действия
  silver/                silver set, слой 1, as_of-запросы
  search/                BM25F, dense, RRF, one-hop, реранкер, метрики
  report.py              раздел результатов из файлов замеров
```

Всё скачанное сохраняется байт-в-байт до парсинга, хешируется и получает запись в манифесте.
Повторный прогон читает из кэша. Цифры в документации **генерируются** командой
`p3 render-results`, а не переписываются руками.

## Ограничения

* **Индекс — обе части НК, 8198 чанков, 815 статей.** Достижимо 331 запрос silver test из
  337 (98%), потолок recall 0.997.
* **Реранкер видит только top-30 слияния**, а 7% эталонных попаданий лежат за 30-й позицией
  и недостижимы для него в принципе — это чинится параметром, а не моделью.
* **Silver set целится не туда.** Статьи слоя 1 — процедура, ради которой строится
  продукт, — задевают лишь 52 пары из 1678 (3%). Recall по нему описывает налоговый поиск
  вообще, а не рабочую нагрузку продукта.
* **Синтетический набор порождён тем же, кто строит индекс**, поэтому меряет структурную
  достижимость нормы, а не языковой разрыв. Golden set из P4 он не заменяет.
* **Границы темпоральных интервалов приближённые.** ИПС даёт дату изменяющего акта, а не
  дату вступления в силу; редакции взяты выборочно. Тест проверяет механику фильтра, а не
  юридический вопрос о том, какая редакция действовала.
* **Реранкер стоит 15–18 секунд на запрос** на GTX 1650 SUPER. Лучшая по качеству конфигурация
  непригодна для интерактивной работы на этом железе.
* **Замеры латентности — сравнение конфигураций между собой**, а не показатели продукта:
  целевое железо P5 — 24 ГБ GPU, здесь 4 ГБ и CPU без AVX2.
* **Условия использования ИПС** не подтверждены. По ст. 1259 п. 6 ГК РФ официальные документы
  госорганов не являются объектами авторских прав; остаточный риск — право изготовителя базы
  данных (ст. 1334) и условия сайта.
