# Темпоральная модель: что построено и чему можно верить

Заявка проекта — не «поиск по НК», а «поиск по НК **на дату**». Этот документ отделяет
то, что действительно измерено, от того, что пока является приближением.

---

## 1. Три уровня и интервалы

По спеке §5: `norm_unit` живёт вечно, `norm_version` — текст в интервале действия,
`chunk` — запись индекса. Средний уровень строится сравнением редакций: если текст пункта в
двух редакциях различается, норма менялась.

Пять редакций части первой за 2019–2026:

| | |
|---|---|
| Норм (`norm_unit`) | 1692 |
| Версий (`norm_version`) | 2894 |
| Норм, которые менялись | **821** |
| Из них в статьях слоя 1 | **71** |
| Максимум версий у одной нормы | 5 |
| Чанков после схлопывания неизменного текста | **3745** из 8970 |

## 2. Чему можно верить, а чему нельзя

**Факт изменения — наблюдение.** Тексты различаются или нет; здесь догадок нет.

**Границы интервалов — приближение, и это принципиально.** Спека §5 перечисляет четыре
несовпадающие даты и прямо называет их путаницу главной ловушкой:

| Поле | Что означает |
|---|---|
| `published_at` | дата официального опубликования |
| `valid_from` | дата вступления редакции в силу |
| `valid_to` | дата утраты силы |
| `applies_from` | дата, с которой норма применяется к правоотношениям (**бывает ретроспективной**) |

Из ИПС известна только **дата изменяющего акта**. Она не равна ни одной из четырёх:
вступление в силу задаётся самим актом и обычно позже. Вдобавок редакции взяты выборочно,
поэтому изменение между двумя срезами приписывается дате более позднего — граница смещена
вперёд ещё и по этой причине.

**Следствие для области применимости.** Построенные интервалы годятся для проверки
**механики фильтра** — выбирается ли та версия, которую фильтр обязан выбрать. Они не годятся
как юридическое утверждение о том, какая редакция действовала на дату. Второе требует разбора
норм о вступлении в силу и относится к вехе с консолидатором.

Заполнить `valid_from` датой редакции и молча выдать это за темпоральную корректность было бы
ровно тем тихим дефектом, против которого написано ТЗ: фильтр заработает, метрики выйдут
правдоподобные, а редакция будет выбираться неверная.

## 3. Фильтр применяется до поиска

`valid_from <= as_of < valid_to`, в обоих каналах, **до** ранжирования. Фильтрация после
поиска позволила бы отсечённым кандидатам занимать места в top-k, и потеря была бы незаметна
на метриках, где темпоральных запросов нет.

`valid_to = 99991231` вместо `null`: фильтр по диапазону однороднее проверки на null.

## 4. Синтетический тест

Приём из спеки §2: взять нормы с ≥2 редакциями и построить запросы «редакция на дату», где
эталон известен по построению. Набор строится поверх вопросов слоя 1 — то есть проверяет
темпоральность **на тех нормах, которые обслуживает продукт**, а не на случайных.

70 запросов по 12 нормам, каждая в двух формулировках (выдержка из требования и живой вопрос),
эталон — конкретная версия, а не просто норма.

### Результат (BM25)

| | |
|---|---|
| Возвращена верная редакция | **60%** |
| Возвращена **чужая** редакция нужной нормы | **0** |
| Норма не найдена вовсе | 28 из 70 |
| Падение recall от фильтра | **2.78 п.п.** (критерий ТЗ: ≤5) |

Ноль во второй строке — главная цифра. Когда норма найдена, редакция всегда правильная,
значит все промахи — это отказы поиска, а не темпоральной модели. Метрика намеренно разделяет
эти два случая: чужая редакция опаснее ненайденной нормы, потому что выглядит правильным
ответом.

### Как читать «падение recall на 2.78 п.п.»

Это **не цена фильтрации** в том смысле, в каком её обычно понимают. Эталон здесь — норма
(`nk1/st93/p3`), а в темпоральном индексе одна норма представлена несколькими версиями.
Без фильтра в выдачу могут попасть сразу две-три версии одной нормы, и любая из них
засчитывается как попадание — то есть у поиска попросту больше попыток. Фильтр оставляет одну
версию и эту фору убирает.

Поэтому корректное прочтение: **фильтр не разрушает поиск** (порог ТЗ ≤5 п.п. выдержан), а
измеренная разница объясняется главным образом схлопыванием дублей, а не потерей релевантных
кандидатов. Настоящую цену фильтрации показала бы метрика на уровне версии, где дубли
невозможны по построению, — и там же живёт цифра 60% из таблицы выше.

## 5. Две ловушки, найденные при построении

**`rdk` не хронологичен.** Редакция 212 датирована 29.12.2020, а 197 — 28.12.2022.
Сортировка редакций по номеру построила бы интервалы задом наперёд: фильтр продолжил бы
работать и выбирать версии — просто не те. Снимки упорядочиваются по дате.

**Смена вёрстки около 2019 года.** Парсер вернул 0 статей на документе в 1.5 МБ и не сообщил
об этом ничем. До 2019 ИПС отдаёт текст сплошняком, без выделенных заголовков статей.
Замечено только по счётчику в отладочной печати. Теперь разбор падает, если крупный документ
не дал ни одной статьи, а темпоральный срез ограничен поддерживаемым диапазоном редакций.
