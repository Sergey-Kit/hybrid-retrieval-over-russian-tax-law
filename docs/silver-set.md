# Silver set: пары «запрос → эталонные нормы»

**Статус:** собрано и построено из двух источников. **1678 пар**, 403 различные статьи,
сплит 1006 / 335 / 337. Критерий ≥300 пар выполнен с запасом.

| Источник | Пар |
|---|---|
| Письма ФНС, обязательные для применения | 1432 |
| Решения по жалобам ФНС | 246 |

Но **объём закрыт, а прицел — нет**, см. §4а. Это главное, что надо знать про этот набор.

## 1. Откуда берётся разметка

Спека §2 предлагает извлекать цитаты норм из текста писем Минфина и ФНС и превращать их
в эталон. Разведка показала способ лучше: **сервис ФНС «Решения по жалобам» размечает
решения сам**. Каждая запись списка несёт одновременно

* **«Темы споров»** — описание спора на естественном языке, и
* **«Статьи НК РФ»** — статьи, к которым ФНС это решение отнесла.

Пример реальной записи:

| Поле | Значение |
|---|---|
| Темы споров | «Истребование информации в виде письменных пояснений в порядке статьи 93 НК РФ в рамках выездной налоговой проверки» |
| Статьи НК РФ | Статья 93 НК РФ |
| Дата и номер решения | от 21 июня 2024 КЧ-2-9/6961@ |

Отсюда пара получается напрямую: `query` = тема спора, `gold` = `nk1:93`.

**Что это даёт.** Спека §10 перечисляет тихий дефект «silver set построен по цитатам, но
нормы не приведены к `norm_unit_id` → совпадения не засчитываются, метрики занижены».
Для этого источника класс ошибки **не возникает по построению**: эталон не извлекается
эвристикой из текста, а берётся из поля, которое заполнило ведомство.

## 2. Побочный результат: независимая проверка нормализатора

В фильтре сервиса 263 темы, из них 251 — ярлыки статей вида «Статья 101.4 НК РФ»,
написанные ФНС. Прогон нормализатора ссылок по этому списку:

| | Результат |
|---|---|
| Ярлыков статей НК распознано | **251 из 251** |
| Не-НК корректно отброшено (КоАП, ГК, Закон 129-ФЗ, постановления) | **12 из 12** |

Это измерение точности на разметке, которую делал не автор парсера. Известный пробел:
«Глава 26.2 НК РФ» не распознаётся — нормализатор работает на уровне статей, глав в нём нет.

## 3. Как строится набор

```
решения ФНС  ->  pair_from_decision  ->  dedup  ->  split  ->  train/dev/test.jsonl
```

**Разметка.** Ярлык «Статья 93 НК РФ» → `nk1:93` через `p3.refs.normalize`. Часть НК
определяется номером статьи (≥143 — часть вторая). Решения, размеченные только не-НК
актами, отбрасываются.

**Дедупликация.** Формулировки тем повторяются почти дословно. Ключ кластера —
тема, из которой убраны ссылки на нормы и все числа: две темы, отличающиеся только
номером статьи, считаются одним шаблоном. Эталоны внутри кластера объединяются.

**Сплит — по кластерам, не по записям**, 60/20/20, фиксированный seed.

Это отступление от спеки, и намеренное. Спека §9 принимает `Recall@20 ≥ 0.9` на silver set
и §7 предлагает на нём же подбирать веса BM25F и параметр RRF — то есть отчётное число
считается на той же выборке, на которой шёл тюнинг. Здесь: **тюнинг только на train и dev,
отчётные числа — один раз на test.** Отсутствие утечки между сплитами проверяется тестом,
а не глазами.

**Тип запроса** размечается автоматически для разрезов §7: есть ли в самом тексте ссылка
на норму и остаётся ли содержательный текст помимо неё —
`lexical_anchor` / `natural_language` / `mixed`. Правило простое намеренно: его можно
проверить глазами на выборке.

## 4. Чем silver set не является

Дословно по §2 спеки, плюс то, что выяснилось на этом источнике:

* **Смещён.** Решения по жалобам — это споры, а не типичные вопросы.
* **Нет негативов.** Спека требует ≥20% случаев «в источниках нет основания для ответа»;
  здесь их нет вовсе.
* **Нет `as_of`.** Темпоральную корректность на нём не измерить — для этого в вехе 2
  строятся синтетические запросы по редакциям ИПС.
* **Эталон — на уровне статьи, не пункта.** ФНС размечает статьями. Поле
  `gold_norm_ids` заполняется до пункта только там, где пункт назван в ярлыке.
* **«Тема спора» — не вопрос налогоплательщика.** Это формулировка ведомства: суше и
  терминологичнее, чем реальный запрос пользователя продукта. Распределение запросов
  ближе к юридическому, чем к бытовому, — и это **отличие от того, что обещает §2 спеки**
  про «живой язык налогоплательщика». Письма Минфина с блоком «Вопрос:» дали бы язык
  ближе к продуктовому; их доступность не подтверждена, см. §5.

Итог: **silver set — инструмент разработки и тюнинга P3. Golden set из P4 — приёмка.**

## 4а. Объём закрыт, прицел — нет

Добавление 1432 пар из писем закрыло критерий по количеству и **одновременно ухудшило
попадание в предметную область продукта**. Цифры до и после:

| | Только решения | + письма |
|---|---|---|
| Пар | 246 | **1678** |
| Различных статей | 176 | 403 |
| Пар, задевающих статьи слоя 1 | 34 (**14%**) | 52 (**3%**) |
| Из них в тестовом сплите | 7 из 50 | **8 из 337** |
| Доля упоминаний статей части второй | 66% | **87%** |

Покрытие статей слоя 1 по всему набору:

```
nk1/st23   12    nk1/st93.1   8    nk1/st31     4
nk1/st88   10    nk1/st93     6    nk1/st100    1
nk1/st126   9    nk1/st129.1  6    nk1/st6.1    0
nk1/st101   8
```

Самая частая статья набора — `nk2/st220` (имущественные вычеты по НДФЛ, 113 упоминаний).
По ст. 6.1, задающей исчисление сроков и лежащей в основе любого вопроса про срок ответа
на требование, запросов **ноль**.

Это не дефект источников и не противоречие ТЗ. Решения по жалобам и письма покрывают всё
налоговое право, а продукт первой версии обслуживает узкий процедурный срез — **разные
популяции**. Но следствие жёсткое:

> **Recall@20 по этому набору характеризует retrieval по налоговому праву вообще,
> а не рабочую нагрузку продукта.** Публиковать его как продуктовую метрику нельзя.

Отдельную цифру по слою 1 по нему тоже не получить: 8 тестовых запросов ничего не измеряют.
Закрывается это не сбором — все доступные источники исчерпаны, — а синтетическим набором
слоя 1, где эталон известен по построению (план, §3а).

## 4б. Синтетический набор слоя 1 — построен

`data/silver/layer1.jsonl`, генератор — `src/p3/silver/layer1.py`.

**36 пар: 18 вопросов × 2 формулировки**, покрывают все десять статей слоя 1 и все пять
типов вопросов из `01-спеки` (тип требования, сроки, перечень истребуемого, объём
обязанности, последствия неответа).

Две формулировки на вопрос — это два реальных входа продукта, а не две категории:

| Вход | Пример | Что проверяет |
|---|---|---|
| Выдержка из требования | «документы представляются в срок, установленный пунктом 3 статьи 93 НК РФ» | у BM25 есть якорь |
| Живой вопрос | «сколько дней даётся на подачу документов по требованию при проверке» | якоря нет, работает только dense |

Эталон у обеих формулировок **общий**, и `cluster_id` тоже — они всегда попадают в один
сплит. Иначе сравнение «якорь против живого языка» пошло бы по разным запросам и потеряло
смысл. Для вопросов про сроки в эталон добавляется ст. 6.1: любой срок исчисляется по ней.

**Защита от выдумывания эталона.** Каждая запись указывает не только норму, но и опорную
подстроку, которая обязана присутствовать в тексте этого пункта. Проверка идёт против
разобранного корпуса, а не против памяти автора: переформулируют норму или переедет пункт —
набор упадёт на тесте. Механизм уже сработал на этапе разработки: запись ссылалась на
ст. 101 как «рассматриваются руководителем», тогда как в тексте «рассмотрены руководителем
(заместителем руководителя)».

**Ограничение, которое нельзя замалчивать.** Набор порождён тем же, кто строит индекс,
поэтому меряет **структурную достижимость нормы, а не языковой разрыв** между тем, как
спрашивает бухгалтер, и тем, как написан закон. Живые формулировки — это golden set из P4,
и синтетика его не заменяет.

## 5. Что осталось сделать

1. **Живой язык от реальных пользователей** — только через golden set P4.
2. **Живой язык пользователя.** Оба наших источника пишет ведомство. Источники с языком
   налогоплательщика проверены и отклонены: у них нет эталона (`data-sources.md` §3).
2. **Письма Минфина** как второй источник — доступность не проверена. Если наберутся,
   они дают более естественный язык запроса и снимают перекос из §4.
3. **Страницы самих решений** (`/rn77/service/complaint_decision/<id>/`) содержат полный
   текст с фабулой — потенциально более богатый запрос, чем тема спора. Не разбирались.
